# 음성입력 PRD v1.0

- 상태: 초안 (Draft)
- 작성일: 2026-08-02
- 관련 기존 기능: 거래 입력 다이얼로그(`TransactionSheet.tsx`) 내 OCR 영수증 입력(카메라 촬영 / 갤러리 선택)

---

## 1. 배경 및 목적

현재 거래 입력 다이얼로그는 "카메라로 촬영" / "갤러리에서 선택" 두 가지 방식으로 영수증 이미지를 OCR 분석해 폼을 자동으로 채워준다. 이 두 로직의 공통 핵심은 **"비정형 입력을 AI가 구조화된 거래 데이터로 변환한다"**는 점이며, 동일한 원리를 음성에도 적용할 수 있다.

목적: 영수증이 없거나(현금 지출 구두 기록, 연금·배당 등 무실물 수입) 사진 촬영이 번거로운 상황에서, 짧은 음성 한 마디로 거래를 등록할 수 있게 한다.

**대상 사용자 특성 고려**: 이 앱은 사용자의 부모님이 실사용자다. 정교한 자유발화 인식보다 "이렇게 말하면 잘 등록된다"는 예측 가능한 패턴을 제공하는 것이 더 중요하다.

---

## 2. 핵심 설계 원칙 (논의를 통해 확정된 방향)

1. **AI는 입력을 대신 채우는 보조 수단이며, 저장 여부는 항상 사람이 최종 확인한다.** 기존 OCR 경로와 동일하게, 음성 인식 결과도 폼에 채워지기만 할 뿐 "저장" 버튼을 눌러야 실제 커밋된다. 완전 자동저장(무확인)은 이번 범위에 포함하지 않는다.
2. **발화 순서를 파서가 강제하지 않는다.** "날짜 → 구분 → 항목/금액 → 비고" 순서는 *사용자에게 안내하는 발화 가이드*로만 제공하고, 실제 파싱은 순서 무관 슬롯 추출(LLM 기반 구조화 출력)로 구현한다. 어순이 달라져도 동작해야 정상이다.
3. **비고(note)는 음성 자동 파싱 대상에서 제외한다.** 기존처럼 사용자가 필요할 때 수동으로 입력한다. (근거: 비고가 여러 항목 중 어디에 적용되는지 발화만으로는 애매성이 남고, 수동 입력이 더 자연스럽다고 판단 — 이번 PRD 논의에서 확정)
4. **수입/지출 구분 누락 시 폴백.** 사용자가 "수입 항목/지출 항목"을 명시하지 않고 항목명만 말한 경우, 기존 OCR의 `categoryMatch`와 동일하게 AI가 항목명(예: "국민연금")으로 구분을 유추한다. 유추 결과는 신뢰도와 함께 미리보기에서 사용자가 확인한다.
5. **기존 자산 재사용.** 새 인프라를 만들지 않고 다음을 재사용한다.
   - STT: `TransactionSheet.tsx`에 이미 연동된 `webkitSpeechRecognition`
   - 구조화 추출 + 분류 매칭: `/api/ocr/route.ts`의 `json_schema` output_config + `categoryMatch` 패턴
   - 다건 미리보기/일괄 저장 UI: `ExcelTools.tsx`의 `PreviewRow` 리스트 패턴

## 3. UX 흐름

### 3-1. 진입점 UI 변경 (탭 메뉴 재구성)

현재 거래 입력 다이얼로그 최상단은 2열 그리드로 "카메라로 촬영" / "갤러리에서 선택" 버튼만 존재한다 (`TransactionSheet.tsx` L358-379).

**변경 후**: 3열 그리드로 재구성하고, 버튼 라벨을 다음과 같이 축약한다.

| 순서 | 라벨 | 아이콘 | 동작 |
|---|---|---|---|
| 1 | 카메라 촬영 | `Camera` | 기존 `cameraInputRef` 트리거 (기존 로직 유지) |
| 2 | 갤러리 선택 | `ImagePlus` | 기존 `receiptInputRef` 트리거 (기존 로직 유지) |
| 3 | 음성 입력 | `Mic` (신규 진입점) | 신규: 음성 입력 모드 진입 |

- 레이아웃: `grid-cols-2` → `grid-cols-3`으로 변경.
- 라벨 축약: "카메라로 촬영" → "카메라 촬영", "갤러리에서 선택" → "갤러리 선택" (요청사항 반영, 3버튼이 한 줄에 들어가도록 텍스트 길이 축소).
- 버튼 순서: 카메라 촬영 → 갤러리 선택 → 음성 입력 (요청된 배열 순서 그대로).
- 기존 비고 필드 옆 마이크 버튼(음성으로 비고만 채우는 기존 기능, L556-571)은 그대로 유지한다. 신규 "음성 입력" 버튼은 비고 한 필드가 아니라 **거래 전체(날짜/구분/항목/금액)**를 채우는 별도 상위 기능이므로 혼동 방지를 위해 다이얼로그 상단 진입점으로 분리 배치한다.

### 3-2. 음성 입력 모드 흐름

1. 사용자가 "음성 입력" 버튼 탭 → 녹음 시작. 큰 원형 버튼이 "듣고 있어요…" 문구와 함께 펄스 애니메이션으로 강조 표시.
2. 사용자가 발화하는 동안, 인식된 텍스트가 실시간 자막처럼 화면에 즉시 표시됨(예: "오늘은 2026년 8월 2일, 수입 항목에는 국민연금 사십오만원..."). 여러 항목을 한 번에 말해도 된다.
3. **발화 종료는 사용자가 같은 버튼을 다시 탭하는 것을 기본 방식으로 한다** (상세 로직은 5-3 참조). 종료 시 소리(짧은 '삐')와 진동으로 명확히 알림.
4. 녹음 종료 직후, AI 파싱을 바로 호출하지 않고 **인식된 원문 텍스트를 큰 글씨로 한 번 더 보여주며 "이렇게 들었어요, 맞나요?"를 확인**한다. 사용자는 "네, 맞아요" 또는 "다시 말할게요"(재녹음) 중 선택.
5. 확인 후 `/api/voice-entry`로 전송.
6. 응답으로 받은 거래 후보 배열의 건수에 따라 UI 분기:
   - **1건**: 기존 OCR과 동일하게 `TransactionSheet` 폼(날짜/구분/금액/분류)에 바로 채워서 단건 확인 화면으로 전환. 비고는 채우지 않고 비워둔다(원칙 3).
   - **2건 이상**: `ExcelTools`의 `PreviewRow` 리스트와 동일한 UI로 전환 — 항목별 카드에 날짜/구분/분류/금액 표시, 신뢰도 낮은 항목은 경고 아이콘, 카드 탭 시 해당 항목만 수정 가능. 상단에 "N건 저장" 버튼.
7. 사용자가 각 항목을 확인/수정 후 저장 버튼 → `addTransaction`을 항목 수만큼 반복 호출 (`source: 'voice'`).
8. 저장 실패/부분 실패 시 `ExcelTools`와 동일하게 결과 메시지(`N건 저장했습니다`) 표시.

## 5. API 설계

### 5-1. 엔드포인트

`POST /api/voice-entry` (신규, `/api/ocr/route.ts`와 동일한 인증/구조 패턴을 따름)

- 인증: 기존 OCR 라우트와 동일하게 Firebase idToken 검증 (`Authorization: Bearer <idToken>`) 후 `decoded.uid === FIREBASE_USER_UID` 확인.
- 요청 바디:
  ```json
  {
    "transcript": "오늘은 2026년 8월 2일, 수입 항목에는 국민연금 45만원, 주식배당 100만원",
    "categories": [{ "name": "연금", "type": "income" }, ...]
  }
  ```
- 응답 스키마 (`json_schema` output_config, `/api/ocr`의 `RECEIPT_SCHEMA`와 동형 구조):
  ```ts
  {
    date: string | null;       // YYYY-MM-DD, 정규화
    entries: {
      itemName: string;        // 발화된 항목명 원문 (예: "국민연금")
      amount: number;
      categoryMatch: {         // 기존 OcrCategoryMatch와 동일 구조 재사용
        matchedName: string | null;
        type: 'income' | 'expense';
        suggestedName: string | null;
        suggestedSubCategories: string[];
      };
      confidence: number;      // 0~1, 항목별 개별 신뢰도
    }[];
  }
  ```
- 비고(note)는 스키마에 포함하지 않는다 (원칙 3 — 수동 입력 유지).

### 5-2. 프롬프트 설계 원칙

- `/api/ocr/route.ts`의 `buildPrompt()`와 동일한 톤으로 작성: 발화 표현의 다양성(예: "오늘은/오늘/오늘 날짜는", "수입 항목에는/수입 항목은")을 일일이 열거하지 않고 "구어체 발화에서 핵심 정보(날짜, 수입/지출 구분, 항목명, 금액)만 추출하라"는 자연어 지시로 일반화한다.
- 순서 비의존: "정보가 어떤 순서로 언급되든 정확히 추출하라"를 명시.
- 구분 누락 폴백: "수입/지출 구분이 명시되지 않으면 항목명으로 미루어 판단하고, 확신이 낮으면 confidence를 낮게 설정하라"를 명시 (원칙 4).
- 금액 표기 다양성 대응: "45만원", "2만3천원", "3천3백원" 등 한국어 숫자 표현을 정확한 정수(원)로 환산하는 규칙을 예시와 함께 명시. (Web Speech API가 브라우저 단에서 이미 숫자를 아라비아 숫자로 변환해주는 경우가 많으므로, 서버 프롬프트는 "이미 숫자화된 표기"와 "한글 숫자 표기"가 섞여 들어올 수 있다는 전제로 작성)
- 기존 분류 매칭/신규 제안 로직은 `/api/ocr`의 categoryMatch 프롬프트 문구를 그대로 재사용.

### 5-3. 클라이언트 STT 연동 변경 — 발화 종료 로직 (60대 사용자 UX 설계)

`TransactionSheet.tsx`

- 기존 `toggleVoiceInput()`(비고 필드 전용)과는 별개로, 음성 입력 모드 진입 시 사용할 새 recognition 인스턴스 로직 추가.

**설계 원칙: "정지 버튼"을 주 메커니즘으로, "무음 감지"는 방치 방지용 보조 안전장치로만 사용한다.**

60대 사용자는 숫자를 떠올리며 문장 중간에 자주 멈춘다("국민연금 사십오... 어 그게, 사십오만원"). 무음 감지를 주 종료 신호로 쓰면 이런 자연스러운 멈춤에서 문장이 조기에 잘리는 실패가 잦다. 반대로 손가락으로 계속 눌러야 하는 워키토키(press-and-hold) 방식은 길게 말할 때 손 피로·오조작 위험이 있어 부적합하다. 따라서 **명시적 탭-투-스타트/탭-투-스톱(토글) 방식을 기본으로 하고, 무음 감지·최대 녹음 시간은 사용자가 종료를 깜빡했을 때만 개입하는 백업**으로 설계한다.

1. **주 메커니즘 — 탭 토글**: 버튼 1회 탭 = 녹음 시작, 같은 버튼 1회 재탭 = 녹음 종료. 사용자가 "내가 끝났다고 누르면 끝난다"는 명확한 통제권을 가짐.
2. **안전장치 ① 무음 타임아웃**: 넉넉하게 8~10초로 설정. 문장 중간의 자연스러운 멈춤은 대부분 이 구간 안에 들어오고, 진짜로 발화를 마친 뒤 종료 탭을 잊고 방치한 경우만 자동 종료로 걸러낸다.
3. **안전장치 ② 최대 녹음 시간**: 60초 상한. 마이크가 실수로 켜진 채 장시간 방치되는 극단 케이스를 막고, API 호출 비용/응답 지연을 관리한다.
4. **실시간 자막(`interimResults: true`)**: 말하는 동안 인식된 텍스트를 화면에 즉시 노출. "잘 듣고 있다"는 시각적 확신을 주는 것이 이 기능의 신뢰도를 좌우하는 핵심 요소 — 자막 없이 로딩 표시만 있으면 인식 여부를 알 수 없어 사용자가 중간에 포기할 위험이 큼.
5. **종료 피드백**: 정지 탭이든 자동 타임아웃이든, 종료 시점에 소리(짧은 '삐') + 진동 + 아이콘 전환으로 명확히 알림. 특히 무음 감지로 자동 종료된 경우 사용자가 "왜 멈췄는지" 모를 수 있어 이 피드백이 더 중요하다.
6. **종료 후 원문 재확인 단계**: STT 텍스트 확정 즉시 AI 파싱(`/api/voice-entry`)으로 넘기지 않고, 인식된 원문을 큰 글씨로 보여주고 "이렇게 들었어요, 맞나요?" 확인을 받은 뒤에만 API를 호출한다(3-2 흐름 4번 참조). 크게 잘못 들었을 경우 API 호출 전에 재녹음으로 되돌릴 수 있어 불필요한 대기와 잘못된 파싱 결과를 사전에 줄인다.
7. 브라우저 미지원 시 기존 `speechSupported` 체크를 재사용해 "음성 입력" 버튼을 비활성화하거나 숨김 처리.

## 6. 비목표 (Out of Scope, v1.0)

- 발화만으로 확인 없이 자동 저장하는 것 (원칙 1).
- 비고 필드의 음성 자동 채움 (원칙 3 — 기존 수동 입력 유지).
- 다국어 지원 (한국어 전용, 기존 `lang: 'ko-KR'` 유지).
- 대화형(turn-based) 확인 질문 흐름(예: "식료품으로 분류할까요?" 같은 AI 되묻기) — 저장 전 미리보기 화면에서의 시각적 확인으로 대체.

## 7. 리스크 및 제약

| 리스크 | 내용 | 대응 |
|---|---|---|
| 모바일 브라우저 호환성 | iOS Safari의 `webkitSpeechRecognition` 연속 인식 안정성이 Android/Chrome 대비 낮을 수 있음 | 기존 `getSpeechRecognitionCtor()` 미지원 체크 재사용, 미지원 시 카메라/갤러리로 유도 |
| 숫자 오인식 | "45만원"과 "4만5천원" 등 자릿수 오인식 가능성 | 항목별 신뢰도 표시 + 저장 전 필수 확인 화면(원칙 1)으로 완화 |
| 다건 발화 시 파싱 난이도 | 항목이 많아질수록 경계 모호성 증가 | 미리보기 리스트에서 항목별 개별 수정 가능하게 설계 |
| 구분 누락 시 오분류 | 수입/지출 생략 발화의 AI 추론이 틀릴 가능성 | 폴백 추론 + 낮은 신뢰도 시 경고 아이콘 (원칙 4) |
| 발화 중 조기 종료 | 무음 감지를 주 종료 신호로 쓰면 숫자를 떠올리며 멈추는 중간에 문장이 잘릴 수 있음 | 탭-투-스톱을 주 메커니즘으로 하고 무음 타임아웃은 8~10초 이상 넉넉하게 설정해 보조 안전장치로만 사용 (5-3 참조) |
